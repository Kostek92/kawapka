# Product Specification: Coffee Pod Ratings

## 1. Purpose

An Android app for keeping a personal collection of coffee capsules and rating the coffees tried. The catalogue is sourced from the Nespresso Original website and includes only individual **Nespresso Original** coffee capsules.

The initial release is a simple single-user app. Multiple profiles are a later feature, but catalogue data must remain distinct from profile-specific data so that feature can be added without changing the meaning of existing collection membership and ratings.

## 2. Scope

### In scope for the first release

- Browse the supported coffee catalogue.
- View coffee images, names, and short descriptions.
- Add coffees from the catalogue to a personal collection and remove them from that collection.
- Rate a coffee from 0.5 to 5 stars in half-star increments, change a rating, or clear a rating.
- Search coffees by name.
- Sort the personal collection by name, intensity, and rating.
- Retain personal data when the app is restarted or the catalogue is refreshed.
- Handle empty results and missing product images without breaking the screen.

### Catalogue boundary

Include individual Nespresso Original coffee capsules only. Exclude Vertuo products, coffee machines, accessories, and offers or bundles that are not individual coffee products. The catalogue source is the Nespresso Original (nespresso.pl) website. The app performs no network requests: the catalogue is a build-time snapshot generated by a script run manually by the developer, so picking up new or removed coffees requires regenerating the snapshot and rebuilding the app. The first iteration ships a small hand-written dummy fixture that the script later replaces.

Support product availability changes and limited editions. If a product disappears from the current catalogue, preserve the product information needed by existing collection entries and do not delete ratings as a side effect of refreshing the catalogue.

Other capsule brands may be considered later, but cross-brand catalogue and import flows are not part of the initial release.

### Explicitly deferred

- Favourites: favourite status and a favourites view. Skipped for the first
  release; the prototype in `docs/prototype/` still shows this flow and is
  outdated in that respect.
- Multiple profiles and profile-to-profile comparison.
- Tasting notes, tasting history, and a “would buy again” flag.
- Advanced filters by intensity, cup size, decaf status, or flavour profile.
- Recommendations, analytics, price tracking, and social features.
- Manual creation/import of coffees outside the supported catalogue.

Do not add deferred features unless requested or unless a small supporting change is necessary for a core feature.

## 3. Product information

Show at least the following for each catalogue coffee when supplied by the backend:

- Stable product identifier (the Nespresso product/SKU code, falling back to a stable slug when no code is available).
- Name.
- Product image, if available.
- Short description, if available.

The catalogue may also provide intensity, recommended cup sizes, flavour/aromatic notes, decaf status, origin, roasting/body/acidity/bitterness descriptors, and availability or limited-edition status. Treat these as optional fields: the app must remain usable when any of them are absent.

A missing image or optional field must not make a product unusable. Do not infer that a coffee is discontinued merely because an optional field or image is missing.

## 4. Personal collection behaviour

The catalogue and a person's collection are different concepts:

- The **catalogue** describes the coffee itself and is shared product information.
- The **personal collection** records which coffees a person has added and their personal choices about those coffees.

For the initial single-user release, the personal collection contains:

- Collection membership (added or not added).
- An optional rating from 0.5 to 5 stars in half-star increments.

A coffee can be added before it has been tried or rated. An unrated coffee is not a zero-star coffee. Do not create duplicate collection entries for the same catalogue product. Removing a coffee from the collection must not delete the catalogue product.

Rating operations must allow setting, changing, and clearing a rating. Clearing the rating returns the coffee to the unrated state. Collection membership should be clear in the UI.

## 5. Search and sorting

- Search the catalogue by coffee name.
- Search results should indicate whether each coffee is already in the personal collection.
- A coffee can be added directly from search results.
- Sort the personal collection by name, intensity, or rating.
- Name sort is alphabetical; intensity and rating sort from highest to lowest.
- Coffees without an intensity and unrated coffees should appear after coffees with a value.
- Use a stable, predictable tie-breaker when sort values are equal.

Do not add full-text search across flavour notes or advanced filtering to the first release.

## 6. Future profiles

When profiles are introduced:

- Each profile has its own collection membership and ratings.
- Personal ratings must never be stored as global properties of a catalogue coffee.
- Comparison shows different profiles' ratings for the same catalogue coffee.
- A profile that has not rated a coffee must remain distinguishable from a profile that rated it one star.
- Existing single-user data must remain intact when profile support is introduced.

The default assumption is multiple profiles on the same device. Account creation, cloud sync, and sharing across phones are out of scope unless explicitly requested.

## 7. Acceptance principles

- The app remains useful if optional catalogue fields are absent.
- Refreshing catalogue data does not erase personal data.
- A catalogue product can exist without being in the personal collection.
- A collection entry can exist without a rating.
- The first release does not require profiles, analytics, recommendations, or advanced filters.
- The app provides useful empty states; because catalogue data is bundled rather than requested at runtime, retry affordances are not required.
